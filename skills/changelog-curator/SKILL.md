# Changelog Curator（把更新日志筛成"能力 + 用法"）

把一份又长又碎的 changelog，减成一份**能快速看清该智能体/工具能力边界与功能用法**的精简版。

## 默认操作方式：就地编辑源文件（极重要）

**在用户给出的源文件（.md）上直接编辑**：按下面规则把该删的条目直接从文件里删掉，该留的原样留在原地。**不要新建输出文件、不要重写整份文档**——除非用户明确要求"另存一份 / 生成新版本 / 输出到别处"。

- 删除 = 从文件中**移除那一条**，不替换成任何说明或总结。
- 保留 = 条目**原文一字不改地留着**。**禁止改写任何保留条目的措辞**——无论原文是"修复 xxx"、"优化 xxx"还是能力描述，保留即原样保留。
- 版本号 `## vX.Y.Z`、日期、分区 `### Core/Desktop/TUI`、链接、标题栏全部保持原样。
- **空锚点删除（递归）**：某版本、某 Build、某日期、某分区下的所有 bullet 都被删光后，该锚点本身也删除——包括它下面独立成行的日期行和 `**Build N**` 标签。先删空 Build，再删因此变空的版本块（版本标题 + 日期整段移除）。读者不需要知道"存在过但没有任何有效信息"的版本。
- 用 `edit` 工具逐条精确删除，改完后 `read` 复查，确保层级结构（标题/日期/分区）仍完整。

### 标题层级规范化

- **正文禁止一级标题（`#`）出现**：changelog 正文里所有版本号、专题、分区一律从二级标题（`##`）起步。
- 若原文用一级标题（如 `# 0.3.21 版本更新`、`# LM Studio API`），批量降级：`^# ` → `## `，原有的二级及以下层级保持不动。
- 降级在全部条目删除完成后进行，避免行号变动干扰。

### 语言精简（去英文留中文）

- **双语 changelog 只保留中文译文**：若源文件是英文原文 + 中文译文交替排列（如每条先英文再中文），**删除所有英文行，只留中文行**。标题行（版本号/日期/分区标签）本身若含双语，也只留中文部分。
- **判定标准**：同一语义内容连续出现两行，第一行为英文、第二行为中文翻译时，删第一行留第二行。若某条目只有英文无中文，则保留英文行（不臆造翻译）。
- 此规则与噪声删除并行执行，但为避免行号干扰，建议在噪声删除完成后统一处理。
- 用 `Edit` 工具逐条删除英文行；也可用脚本批量删除，但改后须 `read` 复查确保中文行完整、无误删。

### 形态无关性

本技能不假设 changelog 一定是 `## vX.Y.Z` + `### Core/Desktop/TUI` 分区形式。也兼容如下变体：

- `## 月份` + `### 日期（分类）` + 粗体标题 + bullet 列表（如二次摘要/翻译型 changelog）
- 任何层级结构（版本、日期、话题、产品等）

**删除单元始终是单条 bullet；锚点单元（版本头、日期头、月份头、分区标签）在其下仍有有效条目时保留，空了则一并删除（见"空锚点删除"）。**

## 目标

原始 changelog 往往混着能力、纯修复、内部优化、贡献者致谢。本文档把它们分开，只留下能让读者回答"它能做什么、怎么用、有哪些限制"的内容。

## 处理规则

### 1. 删除与"能做什么、怎么用"无关的条目

- **纯缺陷修复**（如"修复 xxx 崩溃""修复 xxx 报错"）——除非它改变了行为、输出或限制（见规则 3）。
- **内部性能优化**（如"优化 xxx 启动时间""减少内存增长""加速滚动"）。
- **代码重构、内部架构调整、依赖升级**。
- **测试与构建调整**。
- **贡献者/致谢名单**（`(@xxx)`、Contributors）本身不作为独立内容保留；但它标注的版本号/日期信息仍须保留给对应版本。

**以下十五类在实践中高频出现，一律删除：**

| 噪声类型 | 判定特征 | 典型示例 |
|---|---|---|
| 泛化改进句 | 无场景、无数值、无行为变化，仅说"更可靠/更流畅/更稳定/体验更好" | "长时运行的可靠性提升""两种模式均有体验改进" |
| 版本开头导览句 | 紧跟版本号下、概括"本次更新带来 Bug 修复、UI 改进并新增…"的句式 | "本次更新带来了大量 Bug 修复、UI 改进，并支持 Linux 下的 AMD 9000 系列显卡" |
| 纯呈现/交互调整 | 仅改变视觉呈现或交互细节，不影响功能可用性 | "推理步骤折叠为时间线""紧凑工具卡预览""统一设置键位" |
| UI 外观/字体/主题细节 | 字体大小、字体粗细、主题色、图标、按钮样式、动画、滚动行为等纯外观调整——读者关注的是能力边界，不是皮肤 | "Appearance 标签页新增对话字体大小设置""新增对话字体粗细设置""新增 Solarized Dark 主题""调整消息操作按钮大小" |
| 营销/价值阐释句 | 用"适合…""为…提供…""让…能够…"等句式阐释价值，不陈述事实 | "适合仓库级重构""为安全采购团队提供证据" |
| 内部底座/引擎版本号 | 仅提及底座/框架/内部引擎版本升级或门槛，不附带用户可见能力变化 | "升级到 Code OSS v1.131""依赖 Node.js 18 → 20" |
| 内部引擎依赖门槛 | "需要 xxx-engine X.Y""需要 llama.cpp 引擎 2.5.1 或更高版本""需要 llama.cpp/1.9.0+ 运行时"——是工具内部引擎/库的版本依赖说明，用户感知不到、安装时自动满足 | "需要 mlx-engine/0.3.0""升级 @huggingface/jinja 至 0.5.0""在 mlx-engine 1.0.0 中添加了连续批处理支持" |
| 致谢/贡献者元数据 | "感谢 @xxx""[感谢 @Yorkie](url)""(@contributor)"等附在 bullet 末尾或独立成行的致谢短语——就地删除致谢部分，保留它附着的 bullet 主体；独立成行的致谢 bullet 整条删除 | "新增 lms chat --stats 参数（[感谢 @Yorkie](url)）"→ 保留"新增 lms chat --stats 参数"；"感谢社区翻译者"独立行→整条删除 |
| 效果同义复述 | 与上一条 bullet 重复或近义，仅换说法 | 上一句说"新增浏览器操作"，下一句"代理可在真实浏览器里打开页面" |
| 博客式扩展段 | changelog 中常夹带"## 标题 + 多段正文 + 代码块 + 图片"的博客扩展（原理讲解、技术探讨、性能统计表、教程、论文列表、兼容性实现源码、招聘广告、邮件订阅、社区招募）——整段删除，只保留其中的"参数/命令/限制"条目化陈述 | "技术探讨：滑动窗口注意力公式推导…""我们正在招聘，请将简历发送至…""🔔 订阅我们的邮件列表" |
| 参考性文档表格 | 端点列表、API 参数完整清单、命令选项完整列表、字段对照表等参考性内容——读者需要时查官方文档，changelog 只保留"新增了某端点/某参数"的能力声明，不保留完整参考表 | "`/api/v1/chat` POST / `/api/v1/models` GET / …"端点表、"功能对比表：流式/有状态/MCP/自定义工具 ✅❌"对照表 |
| 纯修复条目（无能力变化） | "修复 xxx 不支持""修复 xxx 报错""修复 xxx 崩溃"等纯缺陷修复——除非改变了对外可见的能力边界、默认值、配额、限制（见规则 3），否则一律删除；不要因为"修复后某场景可用"就保留 | "修复了兼容 OpenAI 接口时 response_format.type 不支持 text 的问题""修复 xxx 崩溃""修复 xxx 报错" |
| 内部实现细节修复（即使算能力变化也删） | "更新 Jinja 模板解析器以支持更复杂模板""重构 xxx 模块""升级构建流程""迁移到新架构"等——即使技术上改变了内部行为，但对用户理解"能做什么/怎么用/有什么限制"毫无帮助，一律删除 | "Bug 修复：更新 Jinja 模板解析器以支持使用更复杂模板的模型""自动化整个构建和发布流程""内部架构调整" |
| 套话/场面话/过渡句 | 情绪表达、自夸、过渡导览、请参阅提示等——与能力/用法/限制无关的纯社交辞令 | "此版本的一大亮点是我们自动化了整个构建和发布流程，我们对此感到非常兴奋""请参阅下面的完整发布更改日志，了解新功能和错误修复""我们很高兴推出" |
| 具体模型/产物上线条目（无配额/上下文等参数） | "支持 GLM4""新增 Qwen3-Coder-480B-A35B 工具支持"等单个模型上线——模型迭代极快、条目迅速过时，除非伴随可度量参数（配额倍率、上下文窗口、最大输出、可用区域、订阅档位、最低客户端版本），否则删除；纯 UI 功能说明中把模型当举例的不删 | "支持 GLM4""新增 Qwen3-Coder-480B-A35B 工具支持""支持 Qwen2VL" |

**关键区分：内部引擎依赖门槛 vs 用户安装前置条件**

- 删除：**工具内部引擎/库/框架**的版本依赖说明（llama.cpp 版本、mlx-engine 版本、@huggingface/jinja 版本、Transformers 版本、Harmony 版本、Outlines 版本、mlx-vlm 版本）——用户安装时自动满足，无需关心。
- 保留：**用户可见前置条件**（Python 版本、操作系统版本、驱动版本、GPU 型号门槛、订阅档位、内存门槛）——这是用户必须自己确认的安装前提。

**关键区分：能力声明 vs 参考性文档**

- 保留："新增 `/v1/responses` 端点""新增 `tool_choice` 参数""新增 `lms ls --variants` 命令"——一句话的能力声明。
- 删除：端点完整列表表、参数完整字段表、命令选项完整清单、功能对照矩阵——读者需要时查官方文档，changelog 不充当 API 手册。

### 2. 保留并突出与能力相关的内容

- **新增能力 / 新特性**：之前没有、现在有的东西（如新增某 provider 支持、新增某命令、新增某开关、新增某文件格式支持）。
- **功能变更与增强**：已有能力的增强（如新增参数、扩大适用范围、更可靠、支持更多场景）。
- **参数或调用方式变化**：命令行参数、配置项、环境变量、快捷键、API 调用方式的增删改。
- **适用范围 / 限制的调整**：支持的平台、模型、区域、文件大小、并发数等边界的变化。
- **废弃项及不兼容变更**：被移除/废弃的能力，以及会破坏既有行为的不兼容变化——这部分最重要，一定要醒目保留。

**两类专题条目的保留细则：**

- **合规/认证条目**（HIPAA、FedRAMP、ISO、GovCloud 等）：保留边界事实——纳入范围、包含/排除的产品、授权以哪个官方清单为准；删除意义阐释和适用对象宣传（如"为采购团队提供证据""联邦机构可使用"）。
- **模型上线条目**：保留可度量参数——积分倍率、上下文窗口、最大输出、可用区域、订阅档位、最低客户端版本、基准分数；删除定位口号（"旗舰""最强"）和场景宣传（"适合仓库级重构"）。

### 3. 若优化/修复确实改变行为、输出、限制或配额，则保留

即便是以"修复/优化"开头的条目，只要它改变了对外可见的行为、输出格式、默认值、速率限制、配额、超时等，也要**原文原样保留**。不要改写。

**快速判据（数字优先）：** bullet 含具体阈值、配额、默认值、超时、价格、版本门槛（如 60 秒、5 个上限、$0.04、0.1x、Python 3.12）的，默认判定为行为/限制变化，优先保留；纯形容词和最高级无可度量对象的，删除。

### 4. 保持版本号、日期与事实准确

- 每个版本号、发布日期、订阅链接保持原样，不臆造。
- 内容只基于原文，**不补充原文没有的信息**。
- 不要让"保留"变成"改写失真"——翻译/精简不得改变语义。
- **复合 bullet 不拆分、不改写**：一条 bullet 用分号并列多件事时，只要含一个可保留要素（命令、参数、数字、限制），就整条原样保留；只有整条全为噪声才整条删除。宁可多留半句，也不破坏"禁止改写"红线。

## 输出形式（就地编辑后的样子）

编辑后仍是**同一份源文档**，层级结构不变，只是条目变少了：

- 每个版本 `## vX.Y.Z` + 日期 保留
- 版本内按 `### Core` / `### Desktop` / `### TUI` 等原分区归类
- 每条保留/删除的 `-` 列表项，直击"能力 / 用法 / 限制"

> 只有用户明确要求"输出到新文件 / 另存"时，才生成一份新文档。

## 审校清单

动手删之前，对每条原始条目过一遍：

- [ ] 这条属于"新能力 / 参数 / 限制 / 废弃"吗？→ 保留（原文原样留）
- [ ] 这条是纯修复 / 纯优化 / 重构 / 致谢吗？→ 删除（从源文件移除）
- [ ] 以"修复/优化"开头的，是否改变了行为 / 输出 / 限制 / 配额？→ 是则整条原文原样保留
- [ ] 保留的条目是否**一字未改**？→ 禁止任何改写
- [ ] 版本号、日期、事实是否与原文一字不差？分区和标题是否仍完整？
- [ ] 是否遗漏了废弃项或不兼容变更？这类最该保留。
- [ ] 批量删除后做一次结构机械校验：空锚点条目数、日期/版本降序、分隔符完整、连续空行、删前删后计数一致。
- [ ] 双语文件是否已删除英文行只留中文？标题行双语部分是否已精简为中文？

## 示例（就地编辑）

**源文件（含噪声）：**
> - 修复 Azure GPT-5.5+ 启用 reasoning 时 completion 请求失败的问题。(@frederiknsgo)
> - 优化标签页 hover、激活和溢出状态。
> - 新增可选择启用的 V2 desktop sidecar，由内置 CLI service 支撑。

**就地编辑后（同一份文件）：**
> - 修复 Azure GPT-5.5+ 启用 reasoning 时 completion 请求失败的问题。(@frederiknsgo)
> - 新增可选择启用的 V2 desktop sidecar。

（第一条：修复但改变了行为/可用性（修复后 GPT-5.5+ 可用 reasoning），按规则 3 整条**原文原样保留**，一字不改；第二条：纯视觉优化，就地删除；第三条：新增能力，原样保留。）

**中文摘要型示例：**

**源文件：**
> - 长时运行的可靠性提升，体验更好。
> - 新增 /goal 命令，代理迭代实现目标并自检完成才结束（默认 5 轮，可配置）。
> - 适合仓库级重构与长周期任务。

**就地编辑后：**
> - 新增 /goal 命令，代理迭代实现目标并自检完成才结束（默认 5 轮，可配置）。

（第一条：泛化改进句，删除；第二条：新增命令 + 含数字阈值，按数字判据保留；第三条：营销阐释句，删除。）
