# Article Tighten Editor（文章精简编辑器）

把一篇 Markdown 文章审读一遍，定位可删的"废话"，然后**直接改到原文件**（用户默认自己用 git 控制版本，无需二次确认）。

## 定位与边界

- 输入：单个 Markdown 文件路径（`*.md`）。也接受目录，此时只处理目录下最大的/用户指定的那一篇。
- 输出：**原地改好的文件**，不新建副本、不改章节顺序、不改作者的表述风格。
- 默认前提：用户在 git 仓库里管理，可随时回退。**不要**创建 `.backup`、不生成 diff 报告文件（用户明确要求时才生成）。
- 边界：只做"删"和"顺手的修错"，**不做**大幅重写、换结构、扩写、润色文风。

## 硬性规则

1. **先全文读完再动手**：用 `read_file` 读完整篇（超过 500 行分页读），不要只看片段就下结论。
2. **证据先行**：每一条删改都要能指出原文位置（章节标题 / 原文句子），不要凭感觉删。
3. **金句保留**：文中有辨识度的短句/金句（如"控制粒度，才能控制结果"）必须保留，删改后重读一遍确认金句都在。
4. **保守删减**：只删确定无信息增量的重复；不确定是否算废话的，保留并在回复中列为"建议但不删"。
5. **结构不动**：不合并章节、不改章节顺序、不改标题编号。
6. **改完必读**：`read_file` 重读修改后的文件，确认 markdown 结构没坏、没有断句、编号顺序已修正。

## Workflow

### 1. 读取输入

1. 用 `search_files`（`target="files"`, `pattern="*.md"`）确认路径存在；用户给的绝对路径直接用。
2. `read_file` 全篇读完，识别文章类型（演讲稿改写 / 教程 / 文档 / 博客），不同类型"废话"的特征不同。

### 2. 按废话类型审读全文（核心判定框架）

逐行扫描，把候选删改点分类归堆：

| 类型 | 识别特征 | 处置 |
|------|---------|------|
| **演讲 PPT 残留** | 无主语要点碎片、`xxx / xxx / xxx` 竖排列表、只有名词的孤行、"我当时觉得…"式感叹 | 若正文已说过，整块删 |
| **提纲/过程残留** | 写作时的提纲、流程串（`A-B-C-D`）、思考过程记录、"后来我发现…" | 删，或压缩成一句话 |
| **跨章节重复论证** | 同一类比/同一件事在两个章节各讲一遍 | 保留信息更完整、场景更具体的一处；另一处删除或改写去重 |
| **同句两说** | 一句话的意思用两种说法连续出现两次 | 二选一保留 |
| **小结整段复述** | 小结把上面各小节的标题又复述一遍 | 压成紧凑清单（要点 + 可选金句一行） |
| **前后逻辑断裂** | 缺连接词、明显漏字（如"而控制上下文长度"应为"不控制"） | 顺手修错 |
| **缺空格/格式** | 中英文混排缺空格、`Repo Wiki助` → `Repo Wiki 助` | 顺手修 |
| **编号顺序错误** | 技巧一→技巧三→技巧二→技巧四 这类 | 修正为自然顺序 |

### 3. 估算可删量

统计候选删改点的总行数，估算占总行数百分比（一般 8%~18% 属正常），告知用户。

### 4. 落地修改

- 用 `edit_file` 做精确替换（`old_str` 必须唯一），或用 `write_file` 重写整个文件（当改动点很多、零散时）。
- 每次替换后确认 `old_str` 唯一；不唯一时改用带上下文的更大片段。
- 修改是**一次性落地**，不生成报告文件。

### 5. 重读校验

`read_file` 重读全文，逐项确认：
- [ ] 目标废话点确实没了
- [ ] 保留的章节/金句都在
- [ ] markdown 结构未破坏（标题层级、列表缩进）
- [ ] 编号顺序已修正（如小结技巧 一二三四）
- [ ] 没有引入断句、错别字
- [ ] 逻辑链完整：问题 → 突破口 → 踩坑 → 技巧 → 实践

### 6. 回复格式

最终回复用简洁清单说明：

```
已删 N 处（约 M 行 / ~X%），改动如下：
- 类型 1：删了 xxx（原文位置）
- 类型 2：压缩了 xxx（原文位置）
- 顺手修错：xxx

保留未删：以下候选保留原样（给出理由）
保留金句：列出保留的关键金句
文件位置：<相对 cwd 的路径>
```

## 安全边界

- **绝不**把"建议删"升级为"必删"；不确定就保留并在回复说明。
- **绝不**改动章节标题编号、章节顺序（除非原编号本身错乱，如小结里技巧一→三→二→四）。
- **绝不**在文件里添加营销套话、表情符号、emoji 或任何不属于原文的内容。
- 用户明确"不要动 X"的部分，即使它是废话也保留。

## 与相邻 Skill 的区别

| Skill | 用途 | 关键差异 |
|-------|------|---------|
| `knowledge-base-cleaner` | 整库清理（备份、图片路径、重复文件） | 不处理单篇文章的废话 |
| `article-dedup-analysis` | 跨文章查重、合并清单 | 只读、不改文件 |
| `technical-article-review` | 打分、给改进建议 | 不落地修改 |
| **本 Skill** | **单篇 Markdown 精简并直接落地** | 唯一会改原文件的 |

## 示例对话

用户："把这个文件改精简一点：/path/to/xxx.md"

Agent：
1. `read_file` 全文读完（143 行）
2. 识别 10 处废话：PPT 残留 5 处、跨章节重复 4 处、小结整段复述 1 处（编号还错乱了）
3. 用 `edit_file` 落地 10 次，其中小结重写为紧凑清单
4. 重读全文校验，金句都在，markdown 结构完整
5. 回复："已删 10 处，约 20 行 / ~14%。保留未删：xxx；保留金句：控制粒度，才能控制结果 / 让 AI 写步骤，不是写系统。文件：10-辅助编程/11-qoder/xxx.md"

用户："帮我改一下这篇文章，直接改文件就行，我 git 管着呢。"

Agent：按上述流程执行，**不**创建备份，**不**生成报告文件，直接原地修改后给出清单。
