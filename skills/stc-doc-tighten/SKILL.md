# STC 技术文档精简

把用户指定的技术文档按简明技术中文（STC）标准做删减和改写，直接在原文件上落地。

## 1. 依据文件

开工前先读标准全文，一切规则以它为准：

`98-标准制定/简明技术中文（STC）写作规范.md`（相对于工作区根目录）

标准更新后本 skill 自动跟随，不在本文件内复制规则全文。

## 2. 适用与不适用

- 适用：操作手册、维护规程、检修卡、SOP、装配指导书、设备说明、安全提示、软件界面文案、API 说明等技术文件；技术博客、厂商案例、工具评测、知识库文章等技术文章。
- 不适用：营销文案、论文、合同、招投标文件。用户给错类型时，说明原因并停止改写，只可给出问题清单供用户决定。
- 输入为目录时，先列出待处理的 Markdown/文本文件清单，让用户确认范围后再动手。

## 3. 工作流程

1. **完整读入**目标文件和 STC 标准全文，不允许只看片段就改。
2. **通览全文**，完成以下标记：
   - 圈出所有 **PR 开场段/主题漂移**（部署范围铺垫、非核心业务线内容）。
   - 圈出所有 **空声明句**（"重新设计了流程"但没说怎么改）、**决策宣布句**（谁批准了什么）、**未来工作无结果段**（"正在开发 X"但无完成指标）。
   - 圈出所有 **直接引语**，按 STC 5.9 三分法分类：
     - 事实性引语（有数据/行为描述）→ 保留原文
     - 评价性/证言式引语（删评价词后无剩余）→ 标记删除
     - 战略套话引语（无时间线、无范围量化、无可验证指标）→ 标记删除
   - 检查 **指标被评价叙事包裹**的段落（评价内容占比>60%）。
   - 检查引语内容是否被叙述**完整覆盖**（无增量信息）。
   - 圈出所有 **商业指标冒充技术成果**（收入、增长、估值、融资）、**成功案例列举**（客户用它做了什么应用）、**社区/生态声明无指标**（"建立了活跃社区"）。这些属面向投资者/媒体的 PR 内容，整段删除。
3. **逐句审读**非引语部分，按第 4 节动作清单标记问题。**精确数据与模糊表述并存时优先删除模糊版**。区分**技术效能指标**（开发周期、准确率、成本）和**商业指标**（收入、增长）——前者保留，后者删除。
4. **执行改写**：用 Edit 在原文件上直接改写，保持原 Markdown 结构（标题层级、表格、代码块、链接）。先删段级废话（PR 开场、空声明、评价性引语段、未来工作段、商业指标段、应用列表段），再改句级问题。
5. **自检**：按标准第 12 节 Checklist 逐项核对。
6. **输出报告**：按第 6 节格式输出。

## 4. 精简动作清单

按以下顺序处理，从内层语法到外层结构：

1. **删形式动词**："对 X 进行/予以/加以/作出 V" → "V X"。
   - "对滤芯进行更换" → "更换滤芯"
2. **删名词化套壳**："完成 X 的采集 / 起到 X 的作用 / 实现 X 的目的" → 直接用动词。
   - "完成数据的采集" → "采集数据"
3. **删无信息成分 + PR 开场段/主题漂移**：语气铺垫（"众所周知""需要注意的是"）、同义重复、无实义引言段。**PR 开场段**（"Anthropic 发布后 Rakuten 于各部门部署..."）、**主题漂移**（非标题核心内容，如文章讲"Claude Code 加速软件开发"但大段落讲非工程师使用场景）→ 整段删除。
4. **拆长句**：操作句超过 20 字、说明句超过 30 字即拆；一句一意，长定语（名词前超过 2 层限定）拆成两句。
5. **拆步骤**：一个编号只保留一个动作；"按下按钮并等待"拆成两步；参数值和预期结果补齐或标记。
6. **改否定**：双重否定改肯定；一句话最多一个否定词；禁令统一用"禁止/不得"。
7. **改被动与主语**：去掉"被、遭、由……所"；操作句以动词开头，第二主体必须写明。
8. **统一术语**：同一概念全文只用一个词。无项目批准词表时，按全文主流写法统一，并在报告中列出统一映射。
9. **清模糊限定**："适当、相关、大概、若干、等"必须替换为可执行表述。"等"字无法穷尽时补"例如：XXX"。`【待确认】` 仅在操作手册/SOP/API 文档等**要求可执行指令**的场景下标记；厂商案例/博客/评测的原文模糊表述**禁止标记待确认**，直接保留原文。
10. **清模糊时长 + 精确数据优先**：操作手册等可执行文档中，"数周、数天、数月"必须精确化或标记 `【待确认】`。**厂商案例/博客中直接保留原文模糊表述**，不标记。同一指标精确数据与模糊表述并存时，直接删除模糊版，保留精确版（所有文档类型适用）。
11. **去行话比喻**：成语、俗语、歇后语、网络用语、多义口语动词改为标准用词。
12. **规范数字单位标点**：阿拉伯数字、法定单位、数值范围两端带单位（"10 A～15 A"）、日期 `YYYY-MM-DD`、中文全角标点。
13. **规范警示**：危险/警告/注意/说明四级标识词不混用，警示句放到它约束的步骤之前，包含"风险来源 + 后果 + 规避动作"。
14. **规范简称**：中文简称和英文缩写首次出现补"全称（简称）"，后文统一。
15. **删新闻叙事框架**：三种常见句式均删除叙事框架，只保留事实本身：
    - 转型叙事："从 X 转型为 Y" → 删除，只写事实。
    - 转折点/标志性事件叙事："X 是关键转折点"/"X 成为标志性事件" → 删除框架，直接写"X 做了什么，导致了什么结果"。
    - 波及叙事："消息发布后，公司都在问"/"X 后，大家都震惊了" → 删除框架，直接写事实。
16. **删结尾升华**：两种常见句式均删除：
    - 意义/价值叙事："X 的意义/价值在于……" → 删除。
    - 范例/样板叙事："X 实践为行业/企业转型提供了范例/样板/标杆" → 删除。
17. **删企业规划层套话**（**判别三特征：无时间线、无范围量化、无可验证指标**）：四种常见句式，整段删除。
    - 战略挂名："X 是我们 Y 战略的一部分" → 删除。
    - 合作理念口号："基于 X 理念合作，以 Y 方式推进 Z" → 删除。
    - 合作理念碎片："加上双方在 X 理念上的一致，促使高层采纳 Y" → 删除理念挂名，只留事实。
    - 无计划扩展声明："正从 X 扩展到 Y 范围/复杂程度" → 删除。
18. **删空声明句 + 删决策宣布句**：
    - **空声明句**："重新设计了流程""而非简单叠加""实现了突破"——声称有改变但未说具体改了什么，如果后文有具体条目，删除声明只留列表。
    - **决策宣布句**："测试结果促使公司高层采纳 X"——讲述谁批准了什么，不是技术事实。
19. **删评价形容词无数据 + 删评价性/证言式引语**：
    - 评价形容词（大幅提升、彻底改变、非常简单、更强执行能力、真正的、完美的、震撼的、非常有效）**无判定标准或实测数据时，整句/整段删除**。
    - **评价性/证言式引语**（Mateos/Desai 等员工证言）：删完所有评价词后如果没有剩下任何具体数据或行为描述，**整个引语段落删除**。
20. **删指标被评价叙事包裹 + 删未来工作无结果段**：
    - **指标被评价叙事包裹**：段落内超过 60% 是赞美引语、情绪叙事、波及叙事，精确数据（如"压缩 79%"）只是点缀——**整段删除**。
    - **未来工作无结果段**：描述"正在开发 X""计划做 Y"但无完成时间、无可验证结果——**整段删除**。例外：如果附带明确的技术设计细节（拆分策略、架构方案），保留技术设计，删除"正在开发"状态词。
21. **直接引语三分法 + 引语重复叙述处理**：
    - **事实性引语（保留）**：有具体数据、操作步骤、测试方法、时间节点。周边叙述（"X 表示""X 回忆道"）按 STC 改写。
    - **评价性/证言式引语（删除）**：删评价词后无剩余，整个引语段落删除（见第 19 条）。
    - **战略套话引语（删除）**：符合第 17 条三特征，整个引语段落删除。
    - **引语完全被叙述覆盖**：如果引语内容已被同文叙述完整覆盖且无增量信息（如引语说"5 个任务 4 个交 Claude Code"，叙述已说过），删除引语。
22. **删商业指标冒充技术成果 + 删成功案例列举 + 删社区声明**：这三类是厂商案例/博客中最常见的"伪成果"，属面向投资者/媒体的 PR 内容，整段删除。
    - **商业指标冒充技术成果**：收入、业务增长、估值、融资额、市场份额——给投资者看的，不是技术内容。**判别**：与"开发周期压缩到 X 小时""根因分析准确率 X%"这类**技术效能指标**（衡量开发效率/质量）严格区分，后者保留。
    - **成功案例列举/客户证言式应用列表**："用户用它做了土地交易应用、感官板、健身追踪器……"是社会证明（social proof），说明"有人在用"，不是技术说明。具体客户做了什么应用对其他开发者无参考价值。
    - **社区/生态声明无指标**："建立了活跃社区""用户分享作品、相互学习""形成了开发者生态"——无数据（社区人数、作品数、日活等）且非技术内容。
    - **核心判别公式**（STC 4.7 第五种子模式）：把这段内容换成"X 公司用它取得了商业成功"这个模板，如果能套进去，就是 PR 内容，删。如果换成"X 技术方法让开发 Y 时 Z 指标提升了 N%"，就是技术内容，留。

## 5. 安全红线

- 不删除任何技术事实：步骤、参数、限值、条件、型号、零件名、警示信息一条不能少，只改表达方式。
- 警示级别只能维持或上调，不得下调。
- 不发明数值、型号、术语。`【待确认：具体内容】` **仅在操作手册/SOP/API 文档**等要求可执行指令的场景下标记；厂商案例/博客/评测的原文模糊数据**禁止标记待确认**（原文就没给，改写者无法补）。详见标准 4.4 节。
- 代码块、命令、公式、表格中的数据原样保留，只改其周边说明文字。
- 精简目标是"更短且更明确"。如果一处删改会损失含义或可执行性，保留原写法并在报告中说明。
- **直接引语的安全红线只保护事实性原话**：引号内有可验证技术事实（数据、行为、方法）的引语保留原文。评价性引语（证言式赞美）和战略套话引语不是事实，整个段落删除**不算违反安全红线**——因为套话和赞美本身无可验证事实。

## 6. 输出报告

改写完成后给出：

1. **统计**：原字数 → 新字数、压缩率、拆分长句数、各类问题处理数量。引语原文不参与压缩率计算（引语保留原文）。
2. **改动明细**：表格列出"章节/原句摘录 → 问题类型 → 修改后"，按动作清单的分类归并。改动明细超过 20 条时只列代表性条目并给出分类计数。
3. **待确认清单**：所有 `【待确认】` 标记的位置和原因，交人工补全。
4. **引语待确认清单**：所有事实性引语内含 STC 违规项的位置（引语本身保留原文），列出引语原文 + 问题类型，交由原文作者决策。评价性/证言式引语和战略套话引语已直接删除，不在此列。
5. **术语统一映射**：无词表时给出"原混用词 → 统一词"对照表。
6. **Checklist 结果**：标准第 12 节逐项打勾，未达标项说明原因（引语内违规项单独标注）。

报告要简短，改动明细超过 20 条时只列代表性条目并给出分类计数。
