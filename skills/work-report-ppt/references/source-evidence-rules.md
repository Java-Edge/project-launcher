# Source Evidence Rules

Use these rules when a work-report deck will be read by leadership, used in a performance review, or used to make project decisions.

## Source hierarchy

Prefer sources in this order:

1. Official KPI/OKR or department target files.
2. Project status reports, meeting minutes, and signed-off stage summaries.
3. Repository evidence: file paths, commits, diffs, tests, CI, issue/PR state.
4. Existing PPTs or docs from prior meetings, as context.
5. User-provided free-form notes, marked as user input if not independently supported.

## Claim discipline

Every non-cover slide should have:

- a conclusion title
- one proof object
- a source-backed support note

Avoid unsupported phrases:

- "已经完成" unless a source shows completion
- "显著提升" unless there is a metric or concrete before/after
- "全面覆盖" unless the source defines the scope and coverage
- "无风险" unless there is explicit risk evidence

Use safer wording when evidence is partial:

- "路径已明确"
- "具备进入验证条件"
- "待资源到位后验证"
- "已识别并形成应对方案"
- "本期不纳入承诺范围"

## Missing evidence

If the source window is empty or a metric is absent:

- do not fill with plausible numbers
- either omit the number or write `待确认`
- put the missing item into "next actions" or "需要支持"

## Risk framing

For each risk, include:

- blocker
- impact
- proposed action
- owner or support needed when known

Do not present a problem as solved if the source only shows an analysis or plan.
